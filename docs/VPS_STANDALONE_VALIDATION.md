## 真实客户端链路

本轮创建内置 Xray 的 VLESS/TCP/REALITY 入站以测试统一订阅。预先选用的 `www.microsoft.com` 目标通过普通 TLS 预检，但真实 REALITY 握手失败。该结果不能算订阅可用。

仅本机监听的临时 Xray 服务对照测试：Microsoft 失败；Tesla 和 Apple 两个目标通过同一条日本 Slot，实际出口为 `219.107.54.157`。临时进程和文件自动清理，公开调试配置已恢复由管理器生成。

目标站点要求参照 [XTLS REALITY 官方说明](https://github.com/XTLS/REALITY)。普通 TLS 1.3 检查不足以证明目标在当前环境下可用于完整 REALITY 链路；每条公开入站仍必须实测。

用户明确授权后，已将本轮入站统一改为 `www.tesla.com:443`，保留原两个入站的端口、UUID 和密钥，并创建第三个入站。管理密码、访问路径及订阅 token 未改动，3x-ui 服务未改配置。

验收从 VPS 外部下载真实 base64 订阅，实际解析其中的 VLESS URI 生成 Xray 客户端配置，不以服务端手写的另一份配置代替。一个订阅含三个节点，服务器地址为 VPS，端口为 `30001/30002/30003`；每条节点分别访问两个 HTTPS IP 查询站点与 Example Domain 内容页，最终同轮三条全部通过。测试主机的网络不代表用户手机的中国大陆 Wi-Fi，手机仍需导入后实测。

俄罗斯出口在前面的外部尝试中出现过 TLS 超时，最终完整同轮复测通过，不能承诺志愿者节点持续稳定；unknown 类型也不能视为已证实家宽。

重启测试暴露并修复了恢复绑定问题：干净关闭后的状态也保留原绑定标记，恢复过程中即便选用了另一个后台节点，入站会重新绑定；同时优先使用当前共享池中的配置，避免旧状态文件覆盖新配置。修复版 `v0.3.1` 的 Linux 和 Python 回归通过，已发布并通过同一安装入口升级；升级后的上述测试未手工重新绑定入站。

## 强杀与自动恢复

仅定位并强杀本项目 Slot 1 的 OpenVPN 进程，没有停止其他出口或 3x-ui。立即进行两次经 `127.0.0.1:17928` 的 HTTPS SOCKS 请求，均返回 curl 97，响应为空，未回落 VPS 公网 IP。随后健康监测自动恢复；Slot 1 仍为 `17928`，出口 `219.107.54.157`，三个 Slot 均重新确认 up。完整故障证据保存在 VPS 项目私有状态目录的 `fault-verification.json`，不含客户端凭据。


第二轮从 VPS 外部使用真实订阅的 `30001` VLESS/REALITY 入站先确认基线，再强杀 Slot 1 的 OpenVPN。两次 HTTPS 请求均返回 curl 35 且响应为空，没有返回母机 IP。健康监测自动拉起新 OpenVPN 进程后，三个入站绑定仍完整；不修改订阅、不手工重新绑定，再次从相同订阅连接 `30001`，两个出口查询及内容检查均通过。原两个入站客户端凭据、REALITY 私钥和订阅 token 与修改前备份一致；3x-ui 仍为 active。

脱敏证据：[三个订阅节点验活](evidence/vps-subscription-20261015.json)、[公开入站断线与恢复](evidence/vps-fault-20261015.json)。证据不包含 UUID、私钥、管理密码、SOCKS 密码或订阅 token。
